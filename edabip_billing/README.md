# EDABIP - Subscription & Billing backend

Backend for the "Billing" screen in the EDABIP frontend, built from
`billing_part.pdf` (the Subscription & Billing requirements - Business
Rules BR-SB-001..012, Acceptance Criteria AC-SB-001..076) and matched
field-for-field against the screenshot of the actual page. **No
frontend files were touched or need to change** - every response shape
below mirrors what the existing UI already renders.

20/20 tests pass (`pytest tests/ -v`) against an in-memory DB with every
Razorpay call mocked, covering plan selection, upgrades, invoices,
payment methods, permissions, search validation, and both webhook
paths (payment succeeded / failed). See "Testing" below.

## Bugs found and fixed in a dedicated audit pass

The first build passed its own test suite, then got a second,
adversarial pass specifically looking for what that suite didn't
cover. It found real issues - a `str`-based Python `Enum` quirk, a
missing SQLAlchemy relationship, a foreign-key constraint, a race
condition, and a webhook gap - each with a regression test added so it
can't silently come back:

1. **`GET /payment-history` crashed (500) on any real data.** The code
   read `payment.invoice` and `payment.payment_method` as ORM
   relationships, but `models.py` only ever defined the `_id` foreign
   key columns, not the relationships themselves. Every normal payment
   has an invoice attached, so this would have failed immediately in
   real use. Fixed by adding the two missing relationships.
2. **Removing a payment method that had ever been charged would fail**
   under MySQL's default foreign-key enforcement (SQLite doesn't
   enforce FKs unless you turn it on, which is why this didn't show up
   until the test fixture was tightened to match MySQL's real
   behavior). Fixed with `ON DELETE SET NULL`, which keeps the
   historical payment record intact - required anyway by the spec's
   data-retention rule - while letting the card itself be removed.
3. **Invoice numbers had a race condition.** They were generated by
   counting existing rows and adding one; two concurrent requests
   could compute the same number and one would fail. Fixed by deriving
   the number from the row's own database-assigned id instead, which
   is race-free by construction.
4. **A `str`-subclass `Enum` gotcha.** `isinstance(x, str)` is always
   `True` for these status enums (they're declared `class X(str,
   Enum)`), so a `... if isinstance(x, str) else x.value` pattern used
   in six places never actually took its `.value` branch. It happened
   to render correctly today because both Pydantic and `csv.writer`
   read the raw string data off these objects directly - but a stray
   f-string anywhere would have printed `PaymentStatus.SUCCESSFUL`
   instead of `successful`. Replaced with an explicit, correct check.
5. **Razorpay's own automatic renewal charges were silently dropped.**
   The webhook handler only *updated* a local invoice it already knew
   about; an invoice from Razorpay's normal recurring billing cycle (as
   opposed to the manual "Renew Subscription" button) has no local row
   to match, so it would never have appeared in the Invoice Table or
   counted toward Total Paid. Fixed by creating the local
   invoice/payment/history rows when none exists yet.

Full acceptance-criteria-by-criteria compliance check (all 76 AC + 12
BR from the spec) is in `COMPLIANCE.md`, including the handful of
items that are genuinely partial or not yet built.

## Integrating into the existing EDABIP backend

1. **Copy `app/` billing files** (`models.py`, `schemas.py`,
   `router.py`, `webhooks.py`, `razorpay_service.py`, `permissions.py`,
   `audit.py`, `config.py`, `seed_plans.py`) into your existing app
   package, e.g. `app/billing/`.
2. **Wire the DB.** Skip `app/database.py` and in every billing file
   change:
   ```python
   from app.database import Base, get_db
   ```
   to whatever your existing project already uses. All billing tables
   are prefixed `billing_*`, so they coexist safely with your existing
   schema either way.
3. **Wire auth/RBAC.** In `app/permissions.py`, replace the two
   fallback imports with your real ones:
   ```python
   from app.auth.dependencies import get_current_user
   from app.models.user import User
   ```
   The only assumptions made about `User` are `.id`, `.org_id`, `.role`
   (string), and optionally `.email`/`.name`. If your app is
   single-tenant (no `org_id`), the simplest fix is to keep an `org_id`
   column defaulted to `1` everywhere - every query is scoped by it, so
   nothing else needs to change.
4. **Mount the routers** in your main app:
   ```python
   from app.billing.router import router as billing_router
   from app.billing.webhooks import router as billing_webhook_router
   app.include_router(billing_router)
   app.include_router(billing_webhook_router)
   ```
5. **Create the tables** (`Base.metadata.create_all(bind=engine)`, or
   generate an Alembic migration if the project already uses one) and
   **seed the plans**: `python -m app.billing.seed_plans`.
6. **Set environment variables** - see `.env.example`.

## Why Razorpay

BR-SB-010 requires payment processing to go through "approved and
secure payment gateways that comply with applicable security and
compliance standards." Razorpay is PCI-DSS compliant and is the
standard choice for an India-based product taking INR payments.

More importantly for "make no mistakes": adding a card goes through
Razorpay Checkout, meaning the actual card number is typed into a
Razorpay-hosted form in the browser and sent straight to Razorpay.
**This backend never receives, sees, or stores a raw card number** -
only Razorpay's generated order/payment/token ids and the
last4/brand/expiry Razorpay returns for display. That eliminates the
entire category of "we mishandled card data" mistakes, and keeps this
server out of PCI scope. Every payment/order-creating call is verified
against Razorpay's signature before we trust it (`utility.verify_*`),
so a tampered or replayed callback can't be used to fake a payment.

Razorpay has no equivalent of Stripe's zero-amount SetupIntent for
"just save a card" - see the docstring at the top of
`app/razorpay_service.py` for how that's handled here (a small
verification charge that's immediately refunded).

Async outcomes (a renewal Razorpay auto-charges on its own schedule, a
refund finishing processing) are reconciled through `app/webhooks.py`,
which is the actual source of truth for payment success/failure - see
the file's docstring for the events to subscribe to in the Razorpay
Dashboard.

## Discrepancies found between the PDF spec and the screenshot

Worth knowing about, none blocking:

| # | Spec (PDF) | Screenshot (frontend) | What this backend does |
|---|---|---|---|
| 1 | Plan names: **Basic / Standard / Enterprise** | **Starter / Professional / Enterprise** | Uses the screenshot's names/prices/features (`starter`/`professional`/`enterprise` codes), since that's what the UI actually renders. |
| 2 | Pricing shown as **₹** (page 3 wireframe) | Pricing shown as **$** | Defaults to `inr` (`BILLING_DEFAULT_CURRENCY`) now that the gateway is Razorpay, matching the wireframe. All amounts are stored as integer minor units, so switching currency later is a config change, not a migration. |
| 3 | - | Header card says current plan is **Enterprise**, but the pricing section tags **Professional** as "Current Plan" | The Usage Overview limits in the screenshot (200 users / 2TB / 5,000 reports / 100 dashboards / 5TB) match the **Enterprise** plan exactly, so Enterprise is almost certainly the real current plan and the "Current Plan" tag on Professional looks like stale mock data. The API always derives `is_current` from the actual subscription, so this resolves itself once real data flows through. |
| 4 | - | "Billing History" card shows **"Total Invoices: $16"** | `$16` is a count (16 invoices) with a stray currency prefix in the mock UI. `BillingHistoryOut.total_invoices` is a plain integer - the frontend's own display template is what adds the "$". |
| 5 | - | Pricing cards don't list a dashboards/data-processing limit | Only Enterprise's dashboard (100) and data-processing (5TB) limits are confirmed (they match the Usage Overview widget). Starter/Professional values in `seed_plans.py` are proportional placeholders marked `PLACEHOLDER` - swap in your real limits before going live. |
| 6 | Usage Analytics metric: **"API Usage"** (page 8) | Usage Overview widget shows **"Reports Generated"** | Went with the screenshot's "Reports Generated" (tracked as `reports_generated`), same reasoning as #1. |

## API reference

All routes are under `/api/billing`. Every response schema is in
`app/schemas.py`; every error message matches the PDF's own copy where
one was specified (search the spec for the exact string to trace it
back).

| Method & path | UI component | Notes |
|---|---|---|
| `GET /search?q=` | Search box | 2-100 chars, `@ . - _` only, matches spec page 5 exactly |
| `GET /overview` | 4 header cards | Plan, period, amount due, last payment |
| `POST /refresh` | Refresh button | Re-syncs from Razorpay first |
| `GET /usage` | Usage Overview (5 widgets) | Pre-formatted `display_used`/`display_limit` strings |
| `GET /storage` | Storage Usage Widget | Dedicated detail view + threshold status |
| `GET /invoices` | Invoice table | Paginated, filterable by status/search |
| `GET /invoices/{no}` / `/download` | Invoice row actions | Download redirects to Razorpay's hosted invoice page |
| `GET /history` | Billing History card + chart | `total_invoices` is an int (see discrepancy #4) |
| `GET/POST/PATCH/DELETE /payment-methods*` | Payment Method list | Card-first flow works even with no subscription yet |
| `GET /payment-history` / `/export` | Payment History | CSV export for Finance Manager/Admin |
| `GET /plans` | Pricing cards | `is_current` computed from the real subscription |
| `POST /plans/{code}/select` | Select/Upgrade Plan buttons | Handles create, upgrade, and downgrade |
| `POST /subscription/renew` | Renew Subscription button | |
| `POST /subscription/cancel` | (spec purpose list item; no dedicated button in the screenshot) | |
| `GET /alerts` / `PATCH /alerts/{id}` | Billing Alerts panel | Acknowledge/dismiss/read |
| `GET /export` | Top-right Export button | CSV of invoices |
| `POST /webhooks/razorpay` | (server-to-server, not user-facing) | Register in Razorpay Dashboard |

## Roles (from the spec's "Users" list)

`administrator` and `billing_administrator` can view + manage (upgrade/
renew/cancel/payment methods) + export. `finance_manager` can view +
export. `client_user` is view-only. Blocked actions return exactly
`"You do not have permission to perform this action."` per the spec's
error table.

## Razorpay setup checklist

1. Nothing to pre-create in the Razorpay Dashboard - unlike Stripe,
   Razorpay Plans are created automatically by this backend the first
   time they're needed (`Plan.razorpay_plan_id` starts empty and gets
   filled in on first use). Plan selection also works end-to-end using
   local invoice/payment records even before that happens.
2. Settings → Webhooks → add endpoint →
   `https://<your-domain>/api/billing/webhooks/razorpay`, subscribed to
   `subscription.charged`, `subscription.pending`,
   `subscription.halted`, `subscription.cancelled`, `refund.processed`.
   Copy the signing secret into `RAZORPAY_WEBHOOK_SECRET`.
3. Frontend side (separate from this backend, noted for completeness):
   the "+ Add New Payment Method" button should call
   `POST /payment-methods/setup-intent`, open Razorpay Checkout with
   the returned `order_id`/`key_id` (pass `"save": 1` so Razorpay
   tokenizes the card), then send the resulting
   `razorpay_order_id`/`razorpay_payment_id`/`razorpay_signature` to
   `POST /payment-methods`.

## Timezone handling

MySQL and SQLite both silently drop timezone info on read even when a
column is declared timezone-aware (verified empirically while building
this). Every datetime this module computes is therefore naive UTC on
purpose (see `_now()` in `router.py`/`webhooks.py`) - don't reintroduce
`datetime.now(timezone.utc)` comparisons against values read back from
the DB, or you'll hit `TypeError: can't subtract offset-naive and
offset-aware datetimes` (this shipped and was caught by the test
suite before being fixed).

## Not included (natural next steps, intentionally out of scope here)

- **Email delivery** for billing alerts (AC-SB-047 requires "in-app
  notifications and email"). `BillingAlert` rows are created correctly;
  wire your existing email-sending utility (you already have one for
  login notifications) into `webhooks.py`'s alert-creation points.
- **Background usage metering** - `UsageRecord` rows exist and are
  created automatically, but nothing increments `active_users`,
  `reports_generated`, etc. yet. That belongs wherever those actions
  actually happen elsewhere in EDABIP (report generation, dashboard
  creation, etc.) - call `UsageRecord` updates from there.
- **Proactive billing alerts** - only `payment_failure` alerts are
  actually created automatically (via the Razorpay webhook, when a real
  charge fails). `subscription_expiry`, `payment_due`,
  `storage_limit_reached`, and `license_expiry` alert *types* exist and
  the API can list/acknowledge them, but nothing checks for those
  conditions proactively - that needs a scheduled job (cron/Celery
  beat/APScheduler, whichever your infra already uses) periodically
  scanning subscriptions and usage records.
- **Usage-limit enforcement** - usage is tracked and displayed against
  plan limits, but nothing here *blocks* an over-limit action (e.g.
  adding a 6th user on a 5-user Starter plan). That check belongs
  wherever users/dashboards/reports actually get created in EDABIP,
  querying this module's usage data first.
- **Historical usage filtering** (AC-SB-016) - `GET /usage` only
  returns the current billing period; there's no way to query a past
  period yet.
- **Razorpay plans** - `Plan.razorpay_plan_id` is nullable and unset
  by default; it's filled in automatically the first time a plan is
  actually selected (see "Razorpay setup checklist" above).

See `COMPLIANCE.md` for the complete acceptance-criteria-by-criteria
breakdown these bullets are pulled from.
